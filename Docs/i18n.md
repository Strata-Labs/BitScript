# Internationalization (i18n) Guide

BitScript uses **`next-i18next`** for chrome (UI strings) and a per-locale
content registry for long-form content (articles, lesson copy). The two
systems share one language switcher driven by Next.js's built-in `i18n`
routing.

Currently configured locales: `en` (default), `fr`, `es`.

---

## Namespace organization

Chrome strings are split across feature-scoped JSON files under
`public/locales/<locale>/`. Pages declare which namespaces they need so
they only ship their own strings, not the whole app's vocabulary.

| Namespace        | What goes in it                                   |
| ---------------- | ------------------------------------------------- |
| `common.json`    | Site-wide stuff (generic buttons, errors, labels) |
| `nav.json`       | NavigationMenu / sidebar / language switcher copy |
| `home.json`      | Landing page / `pages/home.tsx`                   |
| `lessons.json`   | Lessons listing + lesson detail chrome            |

**Add a new namespace when** a feature has more than ~10 strings, or when
its strings would only ever ship on one set of pages (e.g. the
deserializer UI). Naming: lowercase, singular, matches the feature.

**Don't dump everything in `common.json`** — it becomes a 2000-line file
nobody can review, and every page ends up shipping the entire vocabulary.

## Adding a new chrome string

1. Pick a key (snake_case) and the right namespace. Add it to the English
   file first, e.g. `public/locales/en/nav.json`:
   ```json
   { "save_button": "Save" }
   ```
2. Run the parser to mirror the key into other locales as empty strings:
   ```sh
   yarn i18n:extract
   ```
   Then translate `public/locales/fr/nav.json` and
   `public/locales/es/nav.json`.
3. In the component, use the namespace:
   ```tsx
   import { useTranslation } from "next-i18next";

   const { t } = useTranslation("nav");
   <button>{t("save_button")}</button>
   ```
4. The page rendering this component must load the namespace via
   `serverSideTranslations`:
   ```ts
   serverSideTranslations(locale ?? "en", ["common", "nav"])
   ```
   `pages/home.tsx` and `pages/lessons/[lesson].tsx` are the reference
   examples.

## Detecting drift with `i18n:extract`

```sh
yarn i18n:extract
```

This scans `pages/` and `src/` for `t("...")` calls and updates each
locale's namespace JSON files:

- **New keys** appear in English with the inline value (or empty if you
  didn't pass one), and as `""` in `fr`/`es` so untranslated strings are
  visually obvious.
- **Existing translations are never overwritten.** The parser only adds
  keys it doesn't yet see in the file.
- **Removed keys** stay in the JSON (config: `keepRemoved: true`) so you
  can review them before deletion. Once you have a clean baseline you
  can flip this off in `i18next-parser.config.js`.

Run this:
- After every PR that adds new `t()` calls
- Before handing locale files to a translator
- In CI to catch missing translations (future)

## Adding a new article translation

Long-form content (articles, opcode descriptions) lives in `src/const/`
as typed `.ts` files, not JSON, so we keep `ArticleViewProps` typing.

1. Create a sibling file next to the English article, named with the
   locale suffix:
   `src/const/Articles/ECDSAGeneration.fr.ts` →
   `src/const/Articles/ECDSAGeneration.es.ts`
2. Spread the English article and override only what you've translated.
   Anything you don't override stays English, so you can ship
   incrementally. See `ECDSAGeneration.fr.ts` as the reference.
3. Register it in `src/const/Articles/translations.ts`:
   ```ts
   import { ECDSAGenerationEs } from "./ECDSAGeneration.es";

   const es: LocaleArticleRegistry = {
     "ECDSA Generation": ECDSAGenerationEs, // key = English title
   };
   ```
4. Visit `/<locale>/lessons/ECDSA Generation` to see it. Missing
   translations fall back to the English article automatically.

**Keep `href`, `shortHandTitle`, and `lesson` identical to the English
version** so URLs stay stable across locales. Only translate user-facing
text fields (`title`, `description`, `content`).

## Adding a new language

1. Add the locale code to `next-i18next.config.js` `locales` array.
2. Add it to `i18next-parser.config.js` `locales` array too, then run
   `yarn i18n:extract` — the parser creates the new locale folder with
   empty values for every existing key.
3. Translate each namespace JSON in `public/locales/<code>/`.
4. Optionally add an article registry in `translations.ts` (start empty —
   missing articles fall back to English).
5. Optionally add a friendly label in
   `src/comp/LanguageSwitcher.tsx#LOCALE_LABELS`. The switcher works
   without it, just shows the uppercase code.

The switcher reads `router.locales` so the new language appears
automatically.

## Page wiring (when creating new pages)

Every page that uses translations needs to load namespaces:

```tsx
import type { GetStaticProps } from "next";
import { serverSideTranslations } from "next-i18next/serverSideTranslations";

export const getStaticProps: GetStaticProps = async ({ locale }) => ({
  props: {
    ...(await serverSideTranslations(locale ?? "en", [
      "common",
      "nav",
      // + any feature namespaces this page uses
    ])),
  },
});
```

Use `getServerSideProps` instead for dynamic routes (e.g. `[lesson].tsx`).

`NavigationMenu` is rendered globally in `_app.tsx`, so **every page
needs at least `["common", "nav"]`** for the nav chrome to translate.

## URL behavior

- Default locale: `/home` (no prefix)
- Other locales: `/fr/home`, `/es/home`
- The `LanguageSwitcher` preserves the current pathname/query when
  switching, so users stay on the same page.

## Translation workflow tips

- For long-form Bitcoin content, machine translation (LLM) gets ~80%
  there, but a reviewer who knows both the language and Bitcoin
  conventions is needed for terms like "witness", "scriptSig",
  "nonce", and opcode names.
- Maintain a glossary of "do not translate" terms (opcodes, hash
  algorithm names, hex literals).
- When you publish a new English article, locales drift silently —
  `yarn i18n:extract` catches missing chrome keys, but article drift is
  on you. Open a tracking issue when an article is missing translations.
